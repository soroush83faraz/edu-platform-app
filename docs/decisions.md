## 2026-09-20 — DB step 1 (tenancy + iam, roles, RLS, tenant wrapper)

- **Dev DB on host port 5433** (`docker-compose.dev.yml`, volume `pgdata_dev`) to avoid clashing with a local PostgreSQL. Roles/databases are created by `deploy/db/initdb/01-roles.sh` (bash + psql variables instead of the planned `.sql`, so the passwords come from the compose environment without templating).
- **app_owner has no BYPASSRLS** (as specified) and every tenant table is `FORCE ROW LEVEL SECURITY`, so seeds/fixtures written by app_owner must `set_config('app.current_org_id', …, true)` first. System role templates (`iam.role.organization_id IS NULL`) therefore need a second, app_owner-only policy `system_templates`; app_rw can read templates but never write rows with a NULL organization (`tenant_isolation` WITH CHECK). Chosen over granting BYPASSRLS to keep the owner subject to the same rules as everyone else.
- RLS + grants live in idempotent SQL functions `app.apply_rls()` / `app.apply_grants()` (migration `0002_rls_and_grants`); later migrations just call them. `apply_rls` picks the nullable-organization_id policy variant from `information_schema.columns.is_nullable`, so no table is special-cased by name.
- `iam.permission` and `iam.role_permission` are **SELECT-only for app_rw** (seed-managed catalogs; custom roles are out of Phase 1). `drizzle.__drizzle_migrations` is readable by app_rw for `/api/health`.
- Drizzle 0.45 expressed every construct in the spec (generated columns, partial unique indexes, GIN + `gin_trgm_ops`, `num_nonnulls` CHECK, `UNIQUE NULLS NOT DISTINCT`), so `0001_tenancy_iam_tables` is fully generated; only helpers and RLS are custom SQL. Constraint/index names are explicit and short (auto-generated composite FK names exceeded 63 chars).
- Normalizations beyond the spec text: every `boolean` with a default and every `status`-like column is `NOT NULL`; `class_group.status` got `CHECK IN ('active','archived')` (rule: enumerations are text + CHECK); `contact_point` index is `(organization_id, person_id)` (composite-FK friendly) instead of `(person_id)`.
- **`scripts/migrate.js` is pg-only.** Next's standalone output bundles `drizzle-orm` into the route chunks and does not ship it as a package (tracing it in was unreliable across the pnpm layout), so the image runner re-implements drizzle's tiny migration algorithm against the same `drizzle.__drizzle_migrations` table. `scripts/migrate.ts` (local, tsx) uses drizzle's `migrate()`; `tests/int/migrate.test.ts` proves both agree in either order.
- Migration SQL files must be UTF-8 **without BOM** (a BOM makes the first statement fail) and must not contain the literal text `--> statement-breakpoint` outside of real breakpoints (even in comments).
- ESLint: `src/app/api/health/**` may import `@/db/client` (the health probe is the one anonymous DB read); `scripts/**/*.js` may use `require()`.
- `pnpm verify` stays typecheck + lint + unit (no Docker needed); `pnpm verify:full` adds `test:int`. Int tests reset `app_test` by dropping the app-owned schemas as app_owner (no superuser needed) and re-running the migrator; `pnpm db:reset:test` does a full drop/create through `docker compose exec`.

## 2026-09-20 — Auth block (login, sessions, defineAction, seed)

- **Membership lookup at login** (`0003_membership_account_lookup`): `iam.organization_membership` is RLS-bound to the org, but at login the org is unknown. Added `app.current_user_account_id()` + an additive SELECT-only policy `account_memberships` (`user_account_id = app.current_user_account_id()`); the repo binds the setting transaction-locally from the *verified* account row. Chosen over iterating organizations or a SECURITY DEFINER function (FORCE RLS applies to app_owner too, so DEFINER would not bypass it). `apply_rls()` only manages `tenant_isolation`/`system_templates`, so the policy survives re-runs.
- **`can(tx, ctx, permission, ref?)` takes `tx`** and runs inside the action's `withTenant` transaction (spec sketched `can(ctx, …)`): modules may not import `@/db/client`, and one transaction per action is cheaper. `Tx` type is re-exported from `src/lib/actions` so modules can type their `tx` parameter.
- **defineAction order** follows CLAUDE.md (session → must_change_password → Zod strict → can → withTenant → handler), not the spec's "parse first": untrusted input is not parsed before the caller is known. `definePublicAction` is the single pre-auth gate (login only).
- **Implicit permission `iam.account.self`** (own password / own sessions): listed in the catalog, never stored in `role_permission`; `can()` grants it to every authenticated member. Needed because a student's `student` role is scoped to her own `student_profile`, so an org-level `can` would lock her out of the forced password change.
- **Cookie name per environment**: `__Host-session` + Secure in production; plain `session` without Secure in development (browsers reject `__Host-` without Secure, and dev is http://localhost).
- **Sliding session**: the row is extended by `getRequestContext` when < 7 days remain; the cookie can only be re-issued inside a Server Action (`cookies().set` is read-only during render), so `defineAction` re-issues it after a successful action.
- **`Cache-Control: private, no-store`** is set by `src/proxy.ts` on every non-public path. Verified with `pnpm start`: the header survives on production responses; `next dev` overwrites it with its own `no-cache, must-revalidate` (dev only).
- **`Clear-Site-Data`** cannot be set from a Server Action; logout redirects to `/login?out=1` and the proxy adds `"cache", "storage"` to that response. Client-side `caches` deletion waits for the PWA block.
- **Locking windows**: soft lock ≥5/15 min; ≥10 in 1 h → `locked_until = now()+1h`; ≥20 in 24 h → `status='locked'`; (identifier, ip) ≥5/15 min; ip ≥60/10 min. Throttled attempts still run one argon2 verify and still increment `failed_login_count`.
- **Seed**: `scripts/seed.ts` (tsx, own app_owner Pool + Drizzle instance). Deterministic ids (`sha256("edu-demo:"+key)`, v7-shaped) and phones `+98912300xxxx`; re-running resets demo passwords. `guardian_full` got read/comment/notification.read (spec said "row only"; the unit scenarios assume these). No pg-only `seed.js` yet (the catalog is TypeScript) — documented in deploy/README.md as a TODO.
- ESLint `DB_CLIENT_ALLOWED` gained `src/lib/ctx.ts` (the request-context resolver is part of the data-layer boundary).
- **Never round-trip source files through PowerShell `Get-Content | Set-Content`** on this machine: PS 5.1 decodes UTF-8 as the ANSI codepage and re-encodes it, silently turning every Persian string into mojibake (happened to `scripts/seed.ts`, repaired with a cp1256→utf-8 reverse). Use the Edit tool / Python / `sed` in Git Bash.

## 2026-09-20 — DB hardening after the independent verifier's review

- **Per-command RLS policies for nullable `organization_id` tables** (`0004_rls_split_nullable_org_policies`). The verifier refuted the claim "app_rw can read templates but never write them" with a live exploit: a `FOR ALL` policy uses its USING clause to target UPDATE/DELETE rows, so `USING (organization_id IS NULL OR …)` let any tenant `DELETE FROM iam.role WHERE organization_id IS NULL` (1 row) or hijack a template via `UPDATE … SET organization_id = <own org>` (passes the WITH CHECK). `app.apply_rls()` now creates `tenant_isolation_select` (NULL or own org) plus `tenant_isolation_write` / `tenant_isolation_update` / `tenant_isolation_delete` bound to the own org only; `system_templates` (app_owner) is unchanged, NOT NULL tables keep the single `tenant_isolation`. The fix lives in the function (nullability is read from `information_schema`), so `workspace.work_item_type` and any later template table inherit it. Every managed policy name is dropped before recreation, so re-running the function stays idempotent.
- **Constraint triggers guard the two plain FKs into `iam.role`** (`0006_role_tenant_guards`; indexes in the generated `0005_tenant_lookup_indexes`). `role_assignment.role_id` and `role.cloned_from_role_id` cannot be composite `(organization_id, id)` FKs because templates have a NULL organization, and FK checks bypass RLS — org A could attach org B's private role by id. `app.check_role_assignment_role_tenant()` / `app.check_role_cloned_from_tenant()` are `SECURITY DEFINER` (owner app_owner, `SET search_path = pg_catalog, app`) `NOT DEFERRABLE` constraint triggers (`AFTER … FOR EACH ROW` — PostgreSQL does not allow BEFORE constraint triggers, which is the one deviation from the review's sketch). They accept a template (NULL) or the row's own organization and reject everything else with SQLSTATE 23503 + `constraint = <trigger name>`, so `defineAction` maps it to `INVALID_REFERENCE` like a normal FK. Note the DEFINER lookup is still RLS-bound (app_owner has no BYPASSRLS): another tenant's role is NOT FOUND, which is rejected too (fail closed) — the explicit organization comparison is defense in depth for any future BYPASSRLS caller. `RETURNS trigger` functions cannot be called directly, so the DEFINER body has no other entry point.
- **The dump role bypasses RLS** (`0007_backup_role_grants` + `01-roles.sh`). `pg_dump -U app_backup` failed before it read a row: no USAGE on schema `drizzle` (pg_dump locks every table, the ledger included) and FORCE RLS on every tenant table. Alternatives considered: dumping as `app_owner` (also RLS-bound; giving the owner BYPASSRLS would remove the one property that makes seeds honest) or as the `postgres` superuser (works inside the container, but it is not the credential the nightly job gets). Decision: `app_backup` gets `BYPASSRLS` — it holds SELECT-only grants on every app schema plus `drizzle` (tables and sequences, now part of `apply_grants()`), so the attribute widens reads, never writes; `BACKUP_DATABASE_URL` is therefore a full-read credential. The attribute is role-level (superuser), so it lives in `01-roles.sh` for fresh clusters and is a documented one-time operator step on existing servers. `deploy.sh` dumps as `app_backup` too (same role as the future nightly job, so a missing grant fails at deploy time) and now aborts before `migrate` when a dump of an already-migrated database fails, instead of logging and continuing.
- **Guards** (`0008_role_assignment_valid_range` generated from the schema; `0009_updated_at_triggers_fa_norm` custom). `role_assignment_valid_range_chk` (`valid_to IS NULL OR valid_from <= valid_to`). `updated_at` is now set by a `BEFORE UPDATE` trigger (`app.set_updated_at()`) on every base table that has the column, installed by the idempotent `app.apply_updated_at_triggers()` — so the "every migration ends with" rule grew a third call; Drizzle's `$onUpdate` stays for typing but the server value wins (raw SQL, seeds and `ON CONFLICT DO UPDATE` no longer leave stale timestamps). `app.fa_norm` also strips Arabic diacritics U+064B–U+0652 and tatweel U+0640; the ZWNJ→space rule is now spelled `'‌'` instead of an invisible character inside the `translate()` argument (same behaviour, reviewable). `CREATE OR REPLACE` of the IMMUTABLE function does not recompute the STORED `person.search_text`; accepted because no production rows exist, documented in docs/db.md with the PG16/PG17 rebuild recipe. `app_rw` gets `idle_in_transaction_session_timeout = '30s'` and `lock_timeout = '5s'` next to the existing `statement_timeout` — role-level settings, so `01-roles.sh` for fresh clusters plus an operator step on existing ones (`deploy/README.md`).
- **`set_config` is confined to `src/db/client.ts` and enforced by `pnpm verify`** (`scripts/check-forbidden.js`, plain Node, scans application code outside `scripts/`, `tests/`, `drizzle/`). ESLint cannot see inside `sql\`…\`` strings, so a `tx.execute(sql\`select set_config(..., false)\`)` would have passed lint. The one legitimate call outside the wrapper — the login-time `app.current_user_account_id` binding in `src/modules/iam/repo.ts` — moved into `bindAccountContext(tx, id)` in `client.ts` (UUID-validated, transaction-local) and is handed out only as `tools.bindAccount` by `definePublicAction`, i.e. reachable from the pre-auth login path and nowhere else; the repo function now assumes the caller bound the account.
- **Int test files run in alphabetical order (see below)** (`AlphabeticalSequencer` in `vitest.config.mts`). Vitest's default sequencer orders files by cached duration/failures, which changed between runs once more files existed and exposed a latent dependency: `rls.test.ts` asserts the fixture person count, which only holds after `migrate.test.ts` re-seeded following `auth.test.ts`'s inserts.

## 2026-09-20 — DB step 2 (academic, workspace, notif, files, audit, config, integ — 22 tables, 0010 + 0011)

- **No `audit.login_event` table.** The auth block already records every attempt (throttled ones included) in the global `iam.login_attempt(identifier, ip, succeeded, at)`. A second table would duplicate that row and needed its own writer path. Instead `login_attempt` gained two nullable, additive columns: `outcome ∈ success,bad_password,locked,unknown,disabled` (CHECK) and `user_agent`; `loginAction` fills both (`recordAttempt` now takes a record). `succeeded` stays the throttling column, `outcome` is the human-readable reason. Rows written before step 2 keep `outcome = NULL`. The failure response is still byte-identical for every outcome.
- **Global catalogs without RLS:** `workspace.work_item_status` (statuses hang off the type, all types are system types in phase 1) and `notif.notification_type` (codes produced by application code). Seed-managed, `app_rw` SELECT-only through REVOKEs inside `app.apply_grants()` (so re-running the function keeps them), exactly like `iam.permission`. Asserted by `tests/int/rls-meta.test.ts` ("global catalogs"). If tenant-defined work item types ever arrive, `work_item_status` must get a nullable `organization_id` (and inherits the template policies automatically).
- **`audit.audit_log` is append-only for the application**: `REVOKE UPDATE, DELETE … FROM app_rw` lives inside `app.apply_grants()` (0011) because every later migration re-runs the function, which re-GRANTs full DML on ALL TABLES. `src/lib/audit.ts` now inserts (actor person/user, request id, ip, user agent from `Ctx`, before/after jsonb) inside the caller's transaction; `Ctx` gained `ip` + `userAgent`. `entity_id` and the actor columns carry no FK on purpose. Wired into `changePasswordAction` and "logout everywhere"; login stays in `login_attempt`.
- **`class_group.homeroom_staff_id → iam.staff_profile` is declared only in SQL** (`class_group_homeroom_staff_fk`, 0011). `iam.ts` imports `tenancy.ts`, so a Drizzle `foreignKey` on `class_group` would be an import cycle. drizzle-kit does not introspect the database for `generate`/`check`, so the constraint is invisible to it; adding it later in TS would generate a duplicate `ADD CONSTRAINT`. Documented at the column.
- **Exclusion constraint** `class_enrollment_active_excl` (`student_profile_id WITH =, daterange(starts_on, ends_on, '[)') WITH &&` WHERE `status = 'active'`) is custom SQL (Drizzle has no EXCLUDE). It needs `btree_gist`, which the initdb script and `reset-test-db` already create next to `pg_trgm`; 0011 also runs `CREATE EXTENSION IF NOT EXISTS btree_gist` as a no-op safety net (app_owner owns the database, the extension is trusted). Half-open range: an enrollment ended today no longer blocks a new one starting today. `moveEnrollment` sets `ends_on = greatest(current_date, starts_on)` (and `endTeacherAssignment` the same for `valid_to`) so a future-dated row collapses to an empty range instead of tripping the `starts_on <= ends_on` CHECK (added beyond the spec; same for `school_enrollment` and `teacher_assignment`).
- **Derived teacher roles come from the academic service**, not from inserts: `assignTeacher` writes `teacher_assignment` + `role_assignment(role = system 'teacher', scope class_offering, source_type 'teacher_assignment', source_id = assignment)` in one transaction; `endTeacherAssignment` sets `valid_to` and `revoked_at`. The demo seed deletes step 1's hand-inserted teacher rows (`source_type = 'teacher_assignment' AND source_id IS NULL`) once and recreates them through the service, guarded by an existence check so a re-run adds nothing (audit rows included). `moveEnrollment` only moves within the same academic year (`VALIDATION` otherwise); a cross-year move is a new `school_enrollment` and is not in phase 1.
- **`work_item_comment.deleted_at`** is the one deliberate exception to the "no `deleted_at`" rule: the spec asks for soft-deleted comments that keep their slot in a thread. Everything else uses `status` / `archived_at`.
- **Plain FKs `work_item.type_id → work_item_type(id)` and `work_item_status_id`** cannot be composite (system types have `organization_id NULL`), so — like `role_assignment.role_id` before 0006 — a tenant could reference another tenant's private type by id. Accepted for phase 1 because tenant-defined types do not exist (all types are templates); if they arrive, add a constraint trigger like `app.check_role_assignment_role_tenant()`.
- **Seed catalog additions**: 5 system work item types (`todo`, `task`, `admin_request`, `reminder`, `approval`) with 19 statuses (the spec gave `reminder` none; it uses the todo set), 6 notification types. Upserts by natural key; statuses are authoritative per type. `tests/int/seed.test.ts` runs `seedCatalog` twice against `app_test` and asserts identical counts, then recreates the fixture database (later files assert exact template lists).
- **Int fixtures grew an academic graph** (subject, term, class groups, an offering, a student and a staff profile per org, a work_item_type template + one private type, one status, one notification type). Counts in `rls-meta.test.ts` (36 tenant tables, 45 tables) and `guards.test.ts` (26 `updated_at` triggers) were updated accordingly.

## 2026-09-20 — کارتابل (workspace) block: service, read model, notifications, UI

- **Personal-inbox permissions are checked "at any scope"** (`defineAction`/`defineQuery` `scope: "any"` → `canAtAnyScope`). The seed gives teachers their `workspace.*` permissions only through offering-scoped `teacher` assignments and students only through a `student`-scoped role; the organization-level `can()` that a bare `permission` implies would have locked both out of their own کارتابل. The row filters (`inbox_entry.person_id = ctx.personId`, `canViewWorkItem`) are the real boundary for these operations; `assign_class` stays a scoped check inside `createWorkItem` against the concrete offering, and free-form `persons` recipients / org-wide name search require a BROAD assignment (`canBroadly`: organization/school/branch). Unit-tested next to `canPure`.
- **Visibility = creator ∪ inbox entry ∪ broad `work_item.read`**, everything else `NOT_FOUND` (never `FORBIDDEN`) so the existence of an item never leaks. Broad readers see every item of the organization — the spec's phase-1 simplification; per-school partitioning is a later block.
- **Per-assignee completion**: `work_item_assignee.state` is the student's truth (`accepted` = شروع کردم, `done`), the item flips to `done` only when every assignee is done, and each list computes an *effective* category from the viewer's own row (a student who finished sees the item under «انجام‌شده» while the teacher still sees «۱/۱۳ انجام شد»). Creator/broad-admin transitions are authoritative: `done` marks all assignees done, reopening resets them.
- **Comment counts and threads are viewer-aware**: `staff_only` comments are hidden from non-staff (`isStaff` = has `staff_profile`), excluded from their counts, and a non-staff author's `staff_only` request is silently downgraded to `all`. Notifications for a staff-only comment go to staff recipients only.
- **Bucket math is pure TS with a fixed +03:30** (`tehranDayBounds`, `bucketFor`; Iran has had no DST since 1401) and the boundaries are passed to the one-statement `listInbox` SQL, so the DB never needs a time zone. Saturday-start weeks; `(due_at NULLS LAST, id)` keyset cursor. Raw `tx.execute` rows carry timestamps as text (drizzle's pass-through pg parsers) — the repo converts them.
- **`markInboxRead` writes no audit row** (fires on every view; personal state). Pin/archive do.
- **`toResult` now calls `next/navigation` `unstable_rethrow`** instead of only `isRedirectError`: during `next build` a prerender attempt of `/inbox/new` threw Next's `DYNAMIC_SERVER_USAGE`, which `defineQuery` swallowed and logged as a bogus INTERNAL "action failed". Redirect, notFound and dynamic-usage errors now pass through untouched.
- **`next build` workers**: 11 page-data workers crashed natively (0xC0000005 / 0xC0000409 / abort, different each run) on this 8 GB machine with the dev server, Docker and a browser open. `next.config.ts` enables `experimental.memoryBasedWorkersCount` and honours `NEXT_BUILD_CPUS=<n>`; `NEXT_BUILD_CPUS=2 pnpm build` is green. The long-running `next dev` on :3000 was in the same state (render worker dead, `spawn UNKNOWN`), so the walkthrough ran against a fresh `next start -p 3002` of the production build.
- **Demo seed dates**: teacher assignments / enrollments were hard-coded to start on ۱ مهر (2026-09-23), i.e. AFTER the demo days, so `listValidAssignments` returned nothing for کریمی and the teacher could not create anything. `seedDemo` now starts them at `min(today, 2026-09-23)` and backfills existing rows idempotently. Re-run: `SEED_DEMO=1 SEED_DEMO_PASSWORD=… SEED_DEMO_NO_FORCE=1 pnpm seed:demo`.
- **`dir="auto"` on free-text inputs** (title, description, comment) — the one deliberate exception to "no `dir` outside the root": user-typed content may start with Latin/digits and must keep its own direction (spec-mandated for the comment textarea).
- UI decisions: one nav component renders both the phone bottom bar and the `md:` start-side rail so a single poller feeds both badges; the list is summary-first (bucket sections with counts, priority stripe, unread weight) rather than a card grid; pagination is «نمایش بیشتر» = next keyset page + «بازگشت به ابتدا» (no client-side accumulation in phase 1).

## 2026-09-20 — Admin area (`/admin`), people/structure services, Excel import

- **Services first, seed second.** The structure creators (`createSchool` + default branch, `createAcademicYear` + terms, levels/grades/subjects, `createClassGroup`, `createClassOffering` → `assignTeacher`) and the people composites (`createStudent`, `createStaff`, `createAccountForPerson`, `resetInitialPassword`, `unlockAccount`, `assignRole`) live in `src/modules/{tenancy,iam}/service.ts`; `scripts/seed.ts` now finds each demo row by its natural key and either updates it or creates it through the service with its deterministic id (`id?` on the create inputs exists for exactly this and for the importer; admin Zod schemas never carry it). Re-running the seed still yields identical counts; only `audit_log` grows.
- **Admin scope rule** (`getAdminScope`): organization-scoped `iam.admin.access` → whole org; otherwise the caller's school/branch assignments. Enforced inside the transaction after `scope: "any"` (the admin holds the permission at *some* scope; the row filter is the boundary, as in کارتابل). Out-of-scope rows are `NOT_FOUND`. Persons anchored to no school (a student without a class, staff without roles/teaching) are visible to every admin of the organization — the alternative hid a just-created student from the school admin who created him. Org-level catalogs (levels/grades/subjects) and creating schools need an organization-scoped admin.
- **One generic action for the structure resources** (`adminResourceMutate`, permission `iam.admin.access` at any scope, then the resource's own write permission + scope rule + the resource's `.strict()` schema inside the handler) instead of three exported actions per resource: a `"use server"` module may only export async functions, and one entry point keeps `defineResource` at ~100 lines while every mutation still passes `defineAction`'s gate.

## 2026-09-20 — admin scope hardening after verifier review

An independent verifier reproduced seven findings against `app_test`; each fix, the evidence and the resulting rule (`tests/int/admin-scope.test.ts`, docs/admin.md «قانون دامنه»):

- **F1 (critical) — a school admin could take over the organization admin.** `requirePersonInScope` and the SQL `personInScope` treated a person with NO school anchor as visible to every admin, "so the school admin who just created a student could still see them". An `org_admin` holds only an organization-scoped assignment and no enrollment → unanchored → a `school_principal`/`vice_principal` of any school could reset their password, read the decrypted initial password, unlock or edit them (and likewise every student created without a class). Fix: ONE predicate `personInScopeSql` (`src/modules/iam/service.ts`) now backs every list, detail page and account operation: a person holding any unrevoked organization-scoped assignment is outside every school scope, and everyone else needs a POSITIVE anchor in the caller's schools — `school_enrollment` (students), the new `staff_profile.school_id` (staff), or a school-/branch-scoped role (managers). The former "unanchored = visible" clause is gone; unanchored persons are reachable by organization admins only. `requirePersonInScope` runs the same SQL (no TS re-implementation to drift). Consequence: creation must anchor. `createStudent` with a school but no class writes a `registered` `school_enrollment` for the school's current year (`grade_level_id` is nullable since `0012`; `enrollStudent` fills the grade and activates it on the first class); `adminCreateStudent` requires a school or a class from everyone (`VALIDATION` «مدرسه یا کلاس دانش‌آموز را انتخاب کنید.» — F7, instead of the NOT_FOUND an organization admin used to get); `createStaff` stores a primary school (explicit, else the first school role's) and a school-scoped admin must give one.
- **F2 (high) — scope widening through offerings.** `staffOptions` was organization-wide and `offeringResource.create/update` accepted any `mainTeacherStaffProfileId`; `assignTeacher` then produced an offering-scoped derived role that `schoolIdsOfPerson` counted as an anchor → S2's admin could make S1's principal a teacher at S2 and reset their password. Fix: (a) derived teacher roles never anchor a person (they are something the school admin can create himself); (b) `staffAssignableSql`/`requireStaffAssignable` gate both the dropdown and the mutation for school-scoped admins: staff anchored in the scope OR already teaching there (placed by an organization admin — re-using such a teacher for another class of the same school widens nothing because teaching grants no account reach); the importer applies the same check for existing staff when it runs as a school-scoped admin. Chosen over "teaching anchors unless the person holds an admin role elsewhere" because one positive-anchor rule is easier to reason about and to test; the cost is that a visiting teacher's file is managed by their primary school's admins (or the organization admin) only.
- **`staff_profile.school_id` (migration `0012_admin_scope_anchors`).** Nullable, composite FK to `tenancy.school`, partial index. Backfill inside the migration: staff teaching at exactly ONE school and holding no organization/school/branch role get that school; manager-role holders are deliberately skipped (the S1 principal teaching at S2 must not become S2's). Because app_owner is bound by FORCE RLS, the backfill loops over `tenancy.organization` and sets `app.current_org_id` transaction-locally per organization, then clears it — the one `set_config` outside `src/db/client.ts`, in `drizzle/` where `check-forbidden` does not look. The seed derives the demo staff's school (first school role, else the first taught offering) and backfills it on re-run; the staff edit form gained «مدرسهٴ اصلی» (organization admins: any school or none; school admins: only their own schools, never detach). Tested by replaying the `DO $backfill$` block from the migration file inside a rolled-back transaction.
- **F3 (medium) — `revokeRoleAssignment` only checked organization/school scope types.** A school admin knowing a role_assignment id could revoke another school's student-scoped role. Now a school-scoped caller must pass `requirePersonInScope(ra.personId)` and the assignment's scope type must be one they cover (`school`/`branch` inside their schools, `student`); anything else is NOT_FOUND, organization roles stay FORBIDDEN with the explicit message (they were already unreachable through the UI).
- **F4 (low) — `assignRole` had no runtime guard on `roleCode`.** The Zod enum protected the action only; seed/CLI callers could write `teacher` as a manual school-scoped role. The service now allow-lists `org_admin`/`school_principal`/`vice_principal`/`student` before touching the database and checks the role row's `allowed_scope_types` against the chosen scope. A school-scoped caller must also have the target person in scope (previously only the action checked it).
- **F5 (low) — cross-school UUID existence oracle.** `createClassGroup`/`createClassOffering` distinguished «سال تحصیلی یافت نشد» from «به مدرسهٴ این شعبه تعلق ندارد» (and the same for terms), so an S2 admin could test whether a UUID is an S1 year. The services use one field message for both cases (`MESSAGES.yearNotForBranch` / `termNotForClass`), and the resource layer additionally asserts the year/term school is in scope, so for school admins both cases are the same `NOT_FOUND`.
- **F6 (low, functional) — generated usernames collided across organizations.** `login_identifier` is global, school codes are unique per organization and case-sensitively. Fix: `school_org_code_ci_uq` on `(organization_id, lower(code))` plus a case-insensitive `findSchoolByCode` (create pre-check and `--school` lookup); stored codes keep their case. A generated `<code>-<number>` that is taken anywhere gets `-01`…`-05` (`freeGeneratedUsername`); an identifier the admin typed is never rewritten and keeps «این نام‌کاربری قبلاً ثبت شده است.». Rejected: an organization discriminator in every username (longer logins on every credential sheet for a rare collision).
- **Other behaviour changes an operator must know:** (1) after deploying `0012`, staff with `school_id IS NULL` (ambiguous backfill) are visible to organization admins only until «مدرسهٴ اصلی» is set; (2) the student form always needs a school or a class; (3) a school admin no longer sees a visiting teacher's file (only their name on the class/offering pages); (4) `updatePerson` may now be called with only staff fields (the empty person UPDATE is skipped).

The limit is the single Node process: ≈ 50 requests/s per core on the (shared) test laptop, pages p95 ≤ 250 ms at 200 VUs (≈ 35 rps), then queueing — 500 VUs offer ≈ 90 rps and get 51, pages take 5–7 s, still without errors.

Rationale: with one Node process next to Postgres on a 4-vCPU VPS, more than ≈ 2× the DB's cores only moves the queue from the pool into Postgres; 20 keeps `idle in transaction` clients (a connection held while JS runs between statements) from starving requests. `max_connections=100` is now explicit in `deploy/compose.yml` and `docker-compose.dev.yml` (pool + migrate + backup + psql + a second app instance during deploy).

## 2026-09-21 — QA round 1 — auth: unlock vs throttle, password change, personal todos, deep link, Cache-Control

Verbatim QA findings reproduced on the dev server; every fix has a test (`tests/int/auth.test.ts`, `tests/int/workspace-visibility.test.ts`, `tests/unit/{throttle,next-path,password}.test.ts`). docs/auth.md is the source of truth for the resulting rules.

- **B2 (blocker) — «رفع قفل» did not unlock, and retrying the right password escalated to the hour lock.** Two causes. (1) `unlockAccount` only reset `user_account` while `countRecentFailures` kept refusing on the `iam.login_attempt` windows. Fix: additive migration `0014_login_attempt_cleared_at` (nullable `cleared_at timestamptz`); the unlock stamps it on the identifier's uncleared failures of the last 24 h (`clearRecentFailures`) and the counters ignore stamped rows. Chosen over deleting rows (the audit trail stays: who tried what, and when the admin cleared it — `clearedAttempts` lands in the `iam.account.unlocked` audit row) and over an "unlock marker" row (a fake `succeeded` row in the login history would misread as a login). (2) Every refused attempt — throttled, `locked_until`, `status='locked'` — was recorded `succeeded=false` and counted, and `failed_login_count` was incremented with the lock escalation, so the 6th–10th retries during the 15-minute soft lock (even with the RIGHT password) produced `locked_until = +1h`. Fix: an attempt refused without a verdict on the password is recorded with `outcome='locked'` (unchanged audit shape, no CHECK change) but the **identifier** windows skip it (`outcome IS NULL OR outcome <> 'locked'` — NULL = pre-step-2 rows, still counted) and `recordLoginFailure` is not called for it. The **IP** window still counts refused attempts so a sprayer that hammers on through its block stays blocked. The ladder is unchanged in substance — 5 / 15 min soft lock, the 10th counted failure in 1 h → `locked_until`, the 20th in 24 h → `status='locked'` — it is now driven by counted failures only, i.e. at most 20 password guesses per identifier per day, however many times the form is submitted.
- **B2 (c) — the per-IP rule blocked a school NAT at 60 failures / 10 min.** Now ≥ 300 counted failures / 10 min only SLOW every login from that IP by a fixed 1 s (`slowDelayMs`, applied to success and failure alike — no timing oracle) and ≥ 1000 / 10 min refuse (≈ 1.7 failures per second sustained: not a school by hand, and the per-identifier rules already cap what any one account can suffer). A fixed sleep was chosen over an extra argon2 verify: it costs the server nothing and the constant-time property of the login (exactly one verify per attempt) is untouched. The redundant `(identifier, ip)` 5 / 15 min rule stays as written. Rejected: dropping the IP rule altogether (credential spraying across many identifiers is exactly what it is for).
- **M1 (major) — the forced change accepted the temporary password as the new one.** `changePasswordAction` now verifies the new password against the CURRENT hash (one extra argon2 verify) and refuses with «رمز جدید نباید با رمز قبلی یکی باشد.» — in both modes.
- **M2 (major) — the voluntary «تغییر رمز» never asked for the current password.** The voluntary path (decided by `must_change_password` in the DB, never by the form) requires «رمز فعلی», verifies it with exactly one argon2 verify whether or not the account is throttled, and puts a wrong guess into the SAME throttle as the login form: a `login_attempt` row (`bad_password`) for the account's identifier + `failed_login_count++` with the usual escalation, and once the identifier is soft-locked even the right current password is refused with the identical message («رمز فعلی اشتباه است.», `outcome='locked'`). Consequence: an unlocked device has the login form's 5-guesses-per-15-minutes budget; the 20th guess sets `status='locked'`, which also kills that device's session (`getRequestContext` requires `status='active'`). `locked_until` is deliberately NOT checked by `getRequestContext`: an attacker typing a victim's phone number ten times must not log the victim out of her own phone. The refusal is RETURNED from the handler (`{ kind: "current_rejected" }`) rather than thrown, because `defineAction` rolls the transaction back on a throw and the failure record must persist; the public `changePasswordAction` maps it to a `VALIDATION` field error. Audit: `iam.account.password_change_rejected {reason}`, `iam.account.password_changed {revokedSessions, forced}`. Sessions: unchanged — every OTHER session is revoked, the current one stays (verified by the test). UI: `ChangePasswordForm` gets `requireCurrent`; the forced form stays two-field.
- **m5 — managers could open/reopen a person's personal todo.** `canViewWorkItem`: a broad `workspace.work_item.read` no longer reaches a `todo` whose only assignee is its creator (`isPersonalTodo`, one indexed query on `work_item_assignee`, only evaluated on the broad-reader branch). Creator and inbox-entry holders are checked first, so the owner is unaffected; a todo a manager gives to one OTHER person is not personal and stays visible. NOT_FOUND, never FORBIDDEN, as before.
- **m7 — login UX.** The identifier input is controlled (React resets a form's uncontrolled fields after every action, which is why both fields were cleared); `/login?out=1` shows «خارج شدید.»; the deep link is preserved: the proxy redirects a cookie-less protected GET to `/login?next=<path+query>` (without Next's `_rsc` marker; `/` and `/home` are omitted) and `loginAction` redirects there after login. `safeNextPath` (`src/modules/iam/next-path.ts`, import-free so the edge proxy stays lean) accepts only a same-origin relative path: one leading `/`, never `//host` or `/\host`, no backslash / whitespace / control characters, ≤ 512 chars, same origin under WHATWG parsing, not `/login` or `/change-password`; anything else → `/home`. A pending forced change always wins over `next`. Not covered (file owned by another block): the `(app)` layout's redirect for a present-but-dead cookie still goes to plain `/login`.
- **m12 — Cache-Control on private pages.** Reasoned from Next 16.3.5's server source and then confirmed on the load-test standalone build (`node .next/standalone/server.js` on 127.0.0.1:3001, no rebuild): logged in, `/home` and `/inbox` HTML → `private, no-store`, `/api/inbox/summary` → `private, no-store`, the login Server Action POST → `no-cache, no-store, max-age=0, must-revalidate`. From the source: the proxy's `private, no-store` is applied to `res` by the router before the render (`router-server.js` "apply any response headers from routing") and production keeps it — `send-payload.js` sets Next's default only when no `Cache-Control` is present, `send-response.js` (route handlers) never replaces an existing header, and Server Action responses get Next's unconditional `no-cache, no-store, max-age=0, must-revalidate` (`action-handler.js`), which is still `no-store`. Only `next dev` overwrites page responses with `no-cache, must-revalidate` (`base-server.js`, so the browser can restore dev pages on back/forward) — that is what QA saw on http://localhost:3000. No `next.config.ts` change: `headers()` entries are applied at the same point as the proxy's and would be overwritten by the same dev-only code, so they add nothing.
- **c2** — password policy messages use Persian digits (`toLocaleString("fa-IR")`: «۸ نویسه», «۱۲۸ نویسه»); the unit test asserts no ASCII digit in any policy message.

## 2026-09-22 — حضور و غیاب: roll call by زنگ, the student's own month, the admin report (migration 0016)

Owner's ask: the teacher marks the class زنگ by زنگ on their phone in a few seconds; the student sees their own
حضور و غیاب; the principal sees which classes have not been taken today and a per-student absence percentage.
Delivered in phase 1 and moved off the «به‌زودی» list (`/roadmap` now shows it under فاز ۱). Docs: **docs/attendance.md**
(the whole module), docs/admin.md «حضور و غیاب», docs/db.md. Tests: `tests/int/attendance.test.ts`,
`tests/unit/attendance.test.ts`, plus the table-count guards in `tests/int/{rls-meta,guards}.test.ts`.

- **Data (additive, `drizzle/0016_attendance.sql`).** `academic.attendance_session` — one roll call:
  `(organization_id, class_group_id, date, period_no)` **UNIQUE NULLS NOT DISTINCT**. The NULLS NOT DISTINCT is the
  decision: `period_no` NULL means «حضور و غیاب روزانه» (the homeroom roll call), and a plain UNIQUE would treat
  every NULL as distinct, so the same day could collect a dozen identical daily roll calls. With it, re-taking a
  cell UPDATES the row — the product never has two versions of one roll call. `class_offering_id` (nullable,
  composite FK) records the درس of that زنگ; `taken_by_person_id` / `taken_at` is the «ثبت‌شده در …» signature.
  `academic.attendance_entry` — one mark per student (`present / absent / late / excused` by CHECK, optional
  `minutes_late` and note), unique per (session, student), indexed on
  `(organization_id, student_profile_id, status)` for «حضور و غیاب من» and the report totals. No soft delete and
  no history table: a correction is a re-take (the row is updated), and the trail lives in `audit.audit_log`
  (`academic.attendance_session.taken` / `.retaken`, before/after counts).
- **The scope rule — the hard part.** A roll call belongs to a CLASS, but a teacher's role is scoped to a
  `class_offering`. So the service resolves the درس of the cell from `academic.timetable_slot` (weekday of the
  date + period number) and then asks `can()` TWICE: at the `class_group` (org admin, principal, vice — through
  the school) or at that `class_offering` (the teacher of exactly that زنگ). Neither → `NOT_FOUND`, never
  `FORBIDDEN` (docs/admin.md «قانون دامنه»). That is what «the teacher of their own offering at the right period»
  means mechanically: the teacher of زنگ ۲ cannot take زنگ ۴, and a teacher of another class cannot even see the
  class exists. The one widening: the class REPORT is also open to anyone teaching an open offering of that class.
- **Roll-call rules.** The date may never be in the future (Tehran calendar, `isFutureIso`); the زنگ must exist in
  the school's زنگ‌بندی; an explicit درس must belong to the class and not be closed; every student must have an
  active enrollment in that class. `minutes_late` is stored only on «تأخیر». Students dropped from the submitted
  list lose their entry (a roster change), students added get one — the saved roll call always equals the roster
  the teacher confirmed. **Nobody is notified:** phase 1 keeps attendance silent; telling the family is the
  «والدین» module's job, and a notification per absence per day would drown the کارتابل.
- **The roster of a past day ignores `starts_on`.** `listClassRoster(classGroupId, date)` takes the class's active
  enrollments that have not ENDED before that date, but does not require the enrollment to have started by then.
  A `class_enrollment.starts_on` is the day the school registered the student, not the day they walked into the
  room; requiring it would make every seeded (and every freshly imported) class unable to record last week. The
  one-active-class-per-day exclusion constraint still keeps a student out of two rosters.
- **The two percentages are a product decision, not arithmetic.** «درصد غیبت» counts UNEXCUSED absence only
  (`absent / total`) — an absence the school accepted (`excused`) is not held against the student, but it stays in
  the denominator and keeps its own column. «درصد حضور» is `(present + late) / total`: a late student was in
  class. Both live in `src/lib/attendance.ts`, pure and unit-tested, together with the Tehran ISO-date arithmetic
  (`tehranToday`, `weekdayOfIso`, `addDaysIso`, `schoolDaysBetween`) — the same fixed +۰۳:۳۰ the timetable uses.
- **UI.** The teacher's roster is ONE screen: a four-way segmented control per student (each button ≥ 44 px, the
  whole row reachable with a thumb), «همه حاضر», a minutes field that appears only on «تأخیر», and a sticky footer
  with the live count and one primary action — nothing is written until that button, and the whole roll call goes
  in ONE action (one transaction). Chosen over per-row auto-save (25 round trips, no way to see the class as a
  whole before committing) and over a swipe gesture (undiscoverable, and impossible to audit visually).
  A saved roll call reopens pre-filled with «ثبت‌شده در …» above it. The student's page is the month's four
  counts plus the recent marks; the admin page is a GET form (class + range) so a report is shareable and
  printable, with «امروز ثبت نشده» above it.
- **IA.** `/attendance` is one route with three faces, like `/timetable`: the teacher's today, the student's
  month, and a redirect to `/admin/attendance` for an admin who is neither. Home therefore gets exactly ONE tile
  for it — and to keep «one home per destination» literal, `HomeTile.role` now accepts a LIST of hats
  (`role: ["student", "teacher"]`) instead of forcing two tiles at the same href. The admin section has no Home
  tile at all: it lives in `/admin` (`ADMIN_SECTIONS`, after «کلاس‌ها»), the management hub, and there only.
- **Seed.** `scripts/attendance-plan.ts` (pure, hashed) decides every mark: ~۹۲٪ present, ~۴٪ absent, ~۲٫۵٪ late,
  ~۱٫۵٪ excused. `pnpm seed:pilot` writes three weeks for every class — one roll call per school day at the
  class's FIRST زنگ of that weekday, taken through the service by the teacher of that درس with their own ctx, so
  the seeded data exercises the real scope rule and leaves a real audit trail. `pnpm seed:demo` writes the last
  eight school days. Both skip a day that already has a session, so a second run writes nothing
  (`tests/int/seed-pilot.test.ts` compares two runs).

## 2026-09-23 — Admin round 7: «مدرسه‌ها» and «راه‌اندازی» are sections, setup creates a school, the org admin is unique

- **«مدرسه‌ها» and «راه‌اندازی مدرسه» came back into `/admin` as ordinary SECTIONS, organization-admin only**
  (`ADMIN_SECTIONS`, `orgOnly: true`). They have the same entry shape, the same glyph treatment and the same
  pill/rail rendering as دانش‌آموزان · کارکنان · کلاس‌ها · نقش‌ها, and the landing page draws them as two more rows

  component is deleted); its row carries the number the panel carried — **how many steps are still missing** — with
  the hint «گام‌های مانده تا آمادگی برای شروع سال», and the progress bar itself stays on `/admin/onboarding`.
  `SchoolBreakdown` also dropped its «فهرست مدرسه‌ها» link, which would have been a second door to the new row.
- **Both Home tiles are gone for the organization admin**, because one door per destination is a rule *per person*:
  `HOME_TILES.onboarding` is deleted outright, and the `schools` tile is now `adminScope: "school"`. A principal is
  unchanged — a one-school principal still gets «مدرسه» → their own school's hub, a two-school one «مدرسه‌ها» → the
  list — and that is a different destination from the organization's list. `ResourceListPage`'s back link follows
  the same split through `isAdminSectionFor(key, { org })`: no «خانه» back for the organization admin (the rail is
  their way around), «خانه» for a school-scoped admin whose door is the tile. The unit tests now assert the rule as
  «no PERSON sees a destination twice», per persona, instead of a global nav∩tiles check.
- **`/admin/onboarding` step one is actionable.** «مدرسهٴ جدید» is the page's primary action and opens the SAME
